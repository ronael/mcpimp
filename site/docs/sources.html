Documentation · External sources

Import skills from outside the repository.

This guide explains MCPIMP's ingestion layer: how it fetches skills from GitHub or a web catalog, how it keeps them up to date without silent changes, and where to touch the code when your source is not covered yet.

All referenced paths are real and relative to the repository root.

01The idea in one picture

MCPIMP exposes capabilities to an AI client. A capability is a logical unit that can contain several components: a SKILL.md, a mcp.json, resources, and more. Previously, everything was written by hand. The ingestion layer adds a second way to fill the catalog: fetch capabilities from the Internet.

  Internet
     │
     │  ┌──────────────────────────────────────────┐
     │  │  INGESTION LAYER  (offline, explicit,       │
     └──┤  run through `pnpm sources:sync`)       │
        │                                          │
        │   catalog/sources/*.json  declarations  │
        │        ↓                                 │
        │   adapters            github, web-catalog│
        │        ↓                                 │
        │   discovery           which skills?      │
        │        ↓                                 │
        │   fetch               only if changed   │
        │        ↓                                 │
        │   normalization      provenance, license│
        │        ↓                                 │
        │   catalog/capabilities/<namespace>/<slug>/  on DISK         │
        └──────────────────┬───────────────────────┘
                           │
        ┌──────────────────▼───────────────────────┐
        │  MCP RUNTIME  (existing, unchanged)       │
        │   registry → MCP tools → AI client       │
        └──────────────────────────────────────────┘
The golden rule

The MCP runtime never performs network calls. It only reads content already present on disk. If GitHub is down, or if you are offline, your MCP server behaves the same. Synchronization is a separate operation that you trigger.

Practical consequence: an imported capability is a normal folder, committed in Git, readable, diffable, and reversible. Nothing magical happens at runtime.

02Capability anatomy

There are two forms, and the runtime treats them the same. On disk, a capability lives under catalog/capabilities/<namespace>/<slug>/.

Local · written by you
catalog/capabilities/local/landing-page/
  SKILL.md

A folder under the local namespace with at least one supported component, here a SKILL.md.

Imported · written by sync
catalog/capabilities/ui-skills/improve-ui/
  SOURCE.json    ← provenance
  upstream/      ← upstream content
    SKILL.md
    references/
  overrides/     ← your additions

Three zones with very different roles. The public id remains ui-skills-improve-ui.

The three zones and why they exist

SOURCE.json

The identity card. Repository, path, branch, exact commit, content hash, detected license, last sync date, and every file hash. This is what lets you detect later changes and prove where each byte came from.

upstream/

The upstream content as received. It is fully replaced on every resync. Never edit files here: your change would be overwritten without warning.

overrides/

Your zone. Never touched by sync. The registry merges it over upstream/, path by path: same path means your file wins, new path means an added file.

Result: both forms produce the same skill://<id>/<path> URIs. An AI consuming MCPIMP sees no behavioral difference, only an extra origin field on imported capabilities.

03Add a GitHub source

A source is a JSON file in catalog/sources/. The filename must exactly match the id, otherwise sync refuses to start. That is intentional: it prevents silent duplicates.

catalog/sources/ibelick-ui-skills.json
{
  "id": "ibelick-ui-skills",
  "type": "github",
  "repository": "ibelick/ui-skills",
  "ref": "main",
  "roots": ["skills"],
  "namespace": "ui-skills",
  "update": "review",
  "include": ["improve-ui", "baseline-ui"]
}

Every field, one by one

FieldDefaultPurpose
id—Required. Must match the filename.
type—"github" or "web-catalog".
repository—owner/name format. Rejected before any network call if invalid.
refdefault branchBranch or tag. Pinning a tag freezes the version.
rootswhole repositorySubfolders where SKILL.md files are searched. Reduces noise and false positives.
namespacerepository namePrefix for generated ids. Prevents two repositories with a design-system skill from colliding.
includeallSlug allowlist. The slug is the folder containing SKILL.md.
excludenoneSlug denylist. Takes priority over include.
update"review"See section 07.
maxFileBytes524288Per file cap. Larger files are skipped and recorded in skippedAssets.
maxFiles200Guardrail. A larger skill fails the source instead of absorbing a monorepo.
downloadBinariesfalseSee section 09.
notes—Free text. Explain to your future self why this source exists.

Namespace, slug, and public id

On disk: catalog/capabilities/<namespace>/<slug>/. The public id is derived from namespace plus slug, with deduplication when the slug already repeats the namespace. See capabilityIdFor() in src/core/names.ts. Local capabilities use the reserved local namespace; their public id is simply the slug.

local/landing-page/               →  landing-page
ui-skills/improve-ui/             →  ui-skills-improve-ui
matt-pocock/codebase-design/      →  matt-pocock-codebase-design
ui-skills/ui-skills-root/…        →  ui-skills-root  (no duplicate)
Collisions and ownership

An external source can never overwrite a local capability, meaning a folder without SOURCE.json, or take control of a capability owned by another source. Sync checks sourceId and the capability id before any write and refuses conflicts explicitly.

Capability-centric ingestion

The GitHub adapter still discovers roots through SKILL.md, but the sync pipeline consumes capabilities, not skills. A content adapter may return skill-only, MCP-only, or skill+MCP capabilities; MCPIMP stores them with the same namespace/slug identity and provenance model.

04Add a web catalog

A catalog such as agent-design.com, an awesome skills page, or a directory does not contain the skills. It contains links to them. MCPIMP treats it as a discovery source, not a content source.

  catalog page
        │
        │  extract links github.com/owner/repo
        ▼
  owner/repo  ──────► content imported FROM GITHUB
        │
        └──► the catalog is retained as `discoverySource`

The catalog HTML is never scraped into the registry. It is only used to find the original source, then content is imported cleanly from there with its commit and license.

catalog/sources/agent-design.json
{
  "id": "agent-design",
  "type": "web-catalog",
  "url": "https://agent-design.com/skills",
  "roots": [".claude/skills"],       ← applied to EACH delegated repository
  "namespace": "ui-ux-pro-max",
  "include": ["ui-ux-pro-max"],      ← same
  "allowedRepositories": ["nextlevelbuilder/ui-ux-pro-max-skill"]
}
Why allowedRepositories is required

Without it, anyone who gets their repository listed in the catalog could inject a capability into your MCPIMP. The page is third party content you do not control. An empty list means discovery only: sync reports what it found and imports nothing.

The unauthorized list that comes back on every run

That is discovery mode doing its job: it shows the option catalog. To adopt one, add it to allowedRepositories and run sync again.

Known display trap

ibelick/ui-skills appears in this list even though it is imported. This is not a contradiction: it is imported through its own source (catalog/sources/ibelick-ui-skills.json), not through the catalog. The catalog is not allowed to import it. The list should exclude repositories already covered elsewhere; it does not yet.

05Recipes by use case

The situations you will actually run into.

AOne repository = one skill at the root

The SKILL.md is at the root. No roots, no include.

{
  "id": "emilkowalski-skill",
  "type": "github",
  "repository": "emilkowalski/skill",
  "namespace": "emil"
}
The slug becomes the repository name → id emil-skill.
BA multi skill repository

Each subfolder with a SKILL.md becomes a capability. Nothing needs to be coded per skill.

{
  "id": "addyosmani-agent-skills",
  "type": "github",
  "repository": "addyosmani/agent-skills",
  "roots": ["skills"],
  "namespace": "addy"
}
Run first without --apply: you will see the full list of what would be imported, then refine it with include.
CSkills live in a hidden folder

Common with Claude Code plugins: .claude/skills/. It works, you just need to declare it explicitly.

{
  "roots": [".claude/skills"]
}
These skills are often platform-specific because they expect ${CLAUDE_PLUGIN_ROOT}. That is detected and recorded, but you decide whether it is useful outside Claude Code.
DI only want 2 skills out of 12 
{
  "include": ["improve-ui", "fixing-accessibility"]
}
Slugs are folder names, not frontmatter name: values. When unsure, do a dry run: displayed ids tell you the slugs.
EFreeze a precise version

Use a tag instead of a branch: the source will never move by itself.

{
  "ref": "v2.1.0",
  "update": "manual"
}
FThe skill includes images or fonts

By default, binaries are not downloaded: they are recorded in skippedAssets with size, SHA, and URL. You keep traceability without bloating the repository.

If you really need them locally:

{
  "downloadBinaries": true,
  "maxFileBytes": 2097152
}
Mind the weight: the ui-styling skill from ui-ux-pro-max includes 80+ .ttf fonts.
GThe skill contains scripts

They are imported as inert text, indexed, searchable, and never executed by MCPIMP at any point. The capability is classified as executable so the AI knows it contains code.

If you ever want to execute one, it should go through a dedicated, explicit MCP tool. That is outside the current scope.

HRemove a source

Two explicit steps, no automation:

rm catalog/sources/my-source.json
rm -rf catalog/capabilities/local/my-capability
Sync never deletes anything by itself. If a skill disappears upstream, its local capability simply stops appearing in the report; it remains on disk.

06The sync cycle

What happens on every run

1. read catalog/sources/*.json                    (disk)
2. for each GitHub source:
     GET /repos/{owner}/{repo}                → default branch, license
     GET /repos/{owner}/{repo}/commits/{ref}  → THE commit
     GET /git/trees/{commit}?recursive=1      → the whole tree, with one SHA per file
3. group files by folder containing SKILL.md
4. contentHash = sha256( path+SHA of each file, sorted )
5. compare with the local SOURCE.json contentHash
        │
        ├── same  → ✓ up-to-date        NO download
        └── different  → ↑ update-available  + list of changed files
6. if and only if writing is allowed :
     download files, write upstream/, rewrite SOURCE.json
Source health is persisted after every check

Dry-runs, applied runs, and failed runs atomically update logs/source-health.json. The local dashboard and GET /sources reload it without a server restart and keep last check, last applied sync, local/available revisions, errors, and pending changes separate.

The clever bit: 3 requests per repository

The Git tree returns the SHA of every file without downloading file contents. You can know precisely what changed, including which files, without transferring a single byte of content. An unchanged repository costs 3 requests, period.

Statuses

SymbolStatusMeaning
✓up-to-dateNothing moved. No content network call, no write.
↑update-availableNew revision. Added, modified, and deleted files are listed.
−removed-upstreamNo longer discovered upstream. The local copy is kept for an explicit decision.
→renamed-upstreamThe stable upstream path now resolves to another capability id. Both ids are reported.
+newNever imported before. Applied as soon as --apply is used.
✗unavailableUnreachable, invalid, or rejected by a guardrail. Does not interrupt other sources.

Commands

pnpm sources:sync

Read only. Never writes anything. Safe to run.

pnpm sources:sync --apply

Writes new imports and updates under the auto policy.

pnpm sources:sync --apply <capability>

Accepts an update held back by review.

pnpm sources:sync --apply <source>

Same for every capability from that source. Targeting the source also limits the network traversal; targeting a capability cannot.

pnpm sources:sync --json

Machine output, for scripts or CI.

pnpm capabilities:review

Lists imported capabilities whose exact current content still requires review.

pnpm capabilities:review -- <capability> --reviewer <name>

Attests the currently installed contentHash. This action is local and explicit.

Why targeting a capability does not reduce the scan

A capability only exists after discovery: you cannot know which source produces it before reading repositories. The target only applies when deciding whether to write. A source id is known ahead of time and restricts the run (src/ingestion/sync.ts, around line 227).

07Update policy

The problem: a third party repository can change its SKILL.md overnight. If MCPIMP swallowed that automatically, your AI behavior would change without your decision. That is why there are three levels.

PolicyFirst importUpdateUse case
auto--apply--applyA source you control, such as your own repository.
review (default)--apply--apply + name the targetEverything else. You see the diff before accepting.
manual--applysame as reviewIntent marker: do not touch without thinking.

The first import applies as soon as --apply is used, regardless of policy: declaring a source is already a deliberate act. The policy protects evolution, not adoption. The logic fits in five lines: mayWrite() in src/ingestion/sync.ts.

What a held update looks like
↑ ui-skills-improve-ui               update-available
    revision fdc667270f → 9a3f21c8e0
    +1 ~1 -0
      + references/checklist.md
      ~ SKILL.md
    policy "review": run sources:sync --apply ui-skills-improve-ui to accept

08Modify a skill without breaking resync

The natural reflex, editing upstream/SKILL.md, is the trap: the next sync replaces all of upstream/ and your change disappears. Use overrides/.

Add a file
overrides/
  mcpimp-notes.md

New path → added to the capability.

Replace a file
overrides/
  references/plan.md

Same path as upstream → your version wins.

The layer field on each file, visible through capability-info, tells you where it comes from: upstream or override. Useful when auditing local deviations.

Known tradeoff

An override replaces the upstream file; it does not merge it. If upstream improves a file you override, you do not receive those changes automatically. Sync tells you it moved, then you decide what to port. That is the price of simplicity; a three way merge would be disproportionate here.

09Binaries and skill types

Why this was a real problem

The registry used to read every file as UTF-8. One image or font inside an external skill could fill the index with garbage or crash it. Now three checks run in sequence: known binary extension, NUL byte presence, and strict UTF-8 validation. When in doubt, the file is not decoded.

Text file — indexed, searchable, readable through resources/read.
Binary file — metadata retained (size, MIME type, sha256), excluded from readable resources; resources/read returns an explicit error instead of corrupted content.

The 4 detected skill types

Determined during import, recorded in SOURCE.json, purely informational. It never blocks loading.

TypeTriggerWhat it implies
portableSKILL.md + references/Usable everywhere, with no condition.
resource-dependentdata/, assets/, binariesNeeds its files to be useful.
executablescripts/, .py, .sh…Contains code. MCPIMP never executes it.
platform-specific${CLAUDE_PLUGIN_ROOT}, .claude-pluginDepends on a specific host. May not be useful elsewhere.

Priority is descending: a skill with scripts and a platform marker is classified as platform-specific. Raw clues are kept separately in skillTraits. Logic lives in classifySkill(), src/ingestion/normalize.ts.

10Tune search

With 3 capabilities, includes() was enough. With 9, and eventually hundreds, ranking was needed. src/registry/search.ts computes a score in six passes.

1. field weights

The capability name and description weigh 6 and 4; body text weighs 1. A word in a title counts more than a word in the middle of a paragraph.

2. IDF

A word present in every file carries no information and does not lift results.

3. coverage

A file matching 3 words out of 3 beats one matching only one. This makes multi word queries useful.

4. type weights

A SKILL.md ×1.4, a BUNDLE.md ×0.35 because it concatenates everything, and a script ×0.5.

5. resource intent

When the query asks for a resource, reference, link, catalogue or inspiration, resource capabilities and references/ files get a targeted boost.

6. phrase bonus

×1.6 when the query appears as written.

The French / English bridge

Your capabilities may be written in French while AIs often query in English. src/registry/synonyms.ts contains equivalent word groups counted at reduced weight (0.4). That is how photographic luxury can find text about imagerie and haut de gamme.

// add your own domain vocabulary :
["hospitality", "hotel", "hotellerie", "restaurant", "resort"],
["luxury", "luxe", "premium", "upscale", "elegant"],
["saas", "abonnement", "subscription", "b2b"],   ← yours

Constraint: one token per entry, lowercase and accentless. “haut-de-gamme” would not work because the tokenizer would split it.

When you want real semantics

This is not semantic search and does not claim to be. The replacement point is unique: expandTerm(). Plugging embeddings there does not touch any other file. That was the point of the split.

11Extend the code

The most likely case: you want to import from something other than GitHub, such as GitLab, bare Git, an internal API, or a sitemap.

The two ports

In src/ingestion/types.ts. The distinction matters: some sources contain content, while others only point to where it is.

// CONTENT source: can be fetched
interface ContentSourceAdapter<D> {
  type: string;
  getRevision(source: D): Promise<SourceRevision>;              // cheap
  discover(source: D, rev: SourceRevision): Promise<DiscoveredSkill[]>;
  fetch(source: D, skill: DiscoveredSkill): Promise<FetchedFile[]>; // if changed
}

// DISCOVERY source: delegates to a content source
interface DiscoverySourceAdapter<D> {
  type: string;
  getRevision(source: D): Promise<SourceRevision>;
  discoverSources(source: D): Promise<DelegatedSource[]>;
}

Checklist for a new content adapter

1. src/ingestion/types.ts — add your definition interface and put it in the SourceDefinition union.
2. src/ingestion/definitions.ts — add a branch in parseSourceDefinition() to validate your fields. Validate seriously: it is the only barrier before the network.
3. src/ingestion/gitlab.ts — implement ContentSourceAdapter. Go through fetchJson/fetchBytes from http.ts to inherit caps and timeouts, and add your host through extraHosts.
4. src/ingestion/sync.ts — the hard part, see below.
5. A test with a fake server. Copy src/ingestion/__tests__/fake-github.ts: it stubs fetch and lets you simulate a push.
Current limitation to know

sync.ts hard codes the GitHub adapter. Around line 252:

if (source.type !== "github") continue;

With one content adapter, a dispatch table would have been free abstraction. With a second one, it becomes justified: replace this check with a Map<string, ContentSourceAdapter> and retrieve the adapter by source.type. The rest of the loop is already generic; it only manipulates DiscoveredSkill values.

The contract to respect

Three rules, otherwise you break the system guarantees:

Do not download anything in discover().

That is what makes “unchanged = free” true. If your source does not expose a per file hash, use ETag, Last-Modified, or a hash of what you can get cheaply.

Run every path through assertSafeRelativePath().

These strings come from a third party and will become disk writes.

Never lose the exact revision.

Fill origin with the most precise value you have. Without a stable identifier, a content hash is better than nothing.

12Security

A SKILL.md fetched from the Internet is a file written by someone unknown, then read by an AI. That is exactly the profile of a prompt injection. The guardrails:

No execution. Imported scripts are text. Nothing is run during import or loading.
No interpretation during ingestion. The ingester reads bytes and paths. It never “follows” what a file says.
Provenance banner. load-capability prefixes imported content with a reminder: this text is a reference, not an authority. An AI reading “ignore previous instructions” inside it has the context to reject it.
Constrained network. HTTPS required, host allowlist, size caps, timeouts.
Confined writes. Paths are validated against traversal, namespace/slug segments are validated, and every write is rechecked as being under catalog/capabilities/.
No secret exposed. A GITHUB_TOKEN is only sent to api.github.com, never to a third party host.
What this does not protect against

An imported skill can contain bad advice or persuasive instructions. The system guarantees that it does not execute and that it is identified as external, not that it is good. The review policy exists so you read before accepting.

13Troubleshooting

"id" must match the filename

The id field and filename differ. Rename one of them.

GitHub tree … is truncated

The repository is too large for one tree request. Add roots to target the skills subfolder. MCPIMP refuses rather than importing a partial skill.

HTTP 403 for https://api.github.com/…

Quota reached: 60 requests per hour without authentication. Put a GITHUB_TOKEN in .env.

Host not allowed for source ingestion

Host outside the allowlist. For a catalog, its own domain is allowed automatically; for anything else, go through extraHosts in your adapter.

Unsafe upstream path

An upstream path contains .., an absolute path, or a reserved segment. The file is ignored; that means the guardrail works.

A capability does not appear after import

The registry requires at least one supported component, currently SKILL.md or mcp.json, in upstream/ or overrides/. Also check that no local capability uses the same id: local wins.

My changes disappeared

You edited upstream/. Recreate the changes in overrides/, at the same relative path.

Cloudflare deployment does not see new skills

The Worker serves a fixed snapshot. Run pnpm run build after each sync to regenerate generated/capability-snapshot.ts.

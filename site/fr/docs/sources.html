Importer des skills depuis l'extérieur.

Ce guide explique la couche d'ingestion de MCPIMP : comment elle va chercher des skills sur GitHub ou dans un catalogue, comment elle les garde à jour sans jamais se laisser modifier en douce, et où toucher le code quand ton cas n'est pas prévu.

Les chemins cités sont réels, relatifs à la racine du dépôt.

01L'idée en une image

MCPIMP expose des capabilities à une IA cliente. Une capability est une unité logique qui peut contenir plusieurs composants : un SKILL.md, un mcp.json, des ressources, etc. Jusqu'ici tu écrivais tout à la main. La couche d'ingestion ajoute une deuxième manière de remplir le catalogue : rapatrier des capabilities depuis Internet.

  Internet
     │
     │  ┌──────────────────────────────────────────┐
     │  │  COUCHE D'INGESTION  (hors ligne, à la   │
     └──┤  demande, via `pnpm sources:sync`)       │
        │                                          │
        │   catalog/sources/*.json  déclarations │
        │        ↓                                 │
        │   adapters            github, web-catalog│
        │        ↓                                 │
        │   discovery           quels skills ?     │
        │        ↓                                 │
        │   fetch               seulement si changé│
        │        ↓                                 │
        │   normalisation       provenance, licence│
        │        ↓                                 │
        │   catalog/capabilities/<namespace>/<slug>/  sur DISQUE       │
        └──────────────────┬───────────────────────┘
                           │
        ┌──────────────────▼───────────────────────┐
        │  RUNTIME MCP  (déjà existant, inchangé)  │
        │   registry → tools MCP → IA cliente      │
        └──────────────────────────────────────────┘
La règle d'or

Le runtime MCP ne fait jamais d'appel réseau. Il lit uniquement ce qui est déjà sur le disque. Si GitHub tombe, si tu es dans un train sans connexion, ton serveur MCP fonctionne exactement pareil. La synchronisation est une opération séparée que tu déclenches.

Conséquence pratique : une capacité importée est un dossier normal, committé dans Git, que tu peux lire, differ et annuler. Rien de magique au runtime.

02Anatomie d'une capacité

Il y a deux formes, et le runtime ne les distingue pas. Sur disque, une capability vit sous catalog/capabilities/<namespace>/<slug>/.

Locale — écrite par toi
catalog/capabilities/local/landing-page/
  SKILL.md

Un dossier sous le namespace local avec au moins un composant supporté (ici un SKILL.md).

Importée — écrite par la sync
catalog/capabilities/ui-skills/improve-ui/
  SOURCE.json    ← provenance
  upstream/      ← contenu amont
    SKILL.md
    references/
  overrides/     ← tes ajouts

Trois zones aux rôles très différents. L'id public reste ui-skills-improve-ui.

Les trois zones, et pourquoi elles existent

SOURCE.json

La carte d'identité. Dépôt, chemin, branche, commit exact, hash du contenu, licence détectée, date de dernière synchro, et le hash de chaque fichier. C'est ce qui permet de savoir plus tard si quelque chose a bougé — et de prouver d'où vient chaque octet.

upstream/

Le contenu amont, tel quel. Entièrement remplacé à chaque resync. Ne modifie jamais un fichier ici : ta modification serait écrasée sans avertissement.

overrides/

Ta zone. Jamais touchée par la sync. Le registry la fusionne par-dessus upstream/, chemin par chemin : même chemin = ton fichier gagne, nouveau chemin = fichier ajouté.

Résultat : les deux formes produisent les mêmes URIs skill://<id>/<chemin>. Une IA qui consomme MCPIMP ne voit aucune différence — elle voit juste un champ origin en plus sur les capacités importées.

03Ajouter une source GitHub

Une source = un fichier JSON dans catalog/sources/. Le nom du fichier doit être exactement l'id, sinon la sync refuse de démarrer (c'est volontaire : ça évite les doublons silencieux).

catalog/sources/ibelick-ui-skills.json
{
  "id": "ibelick-ui-skills",
  "type": "github",
  "repository": "ibelick/ui-skills",
  "ref": "main",
  "roots": ["skills"],
  "namespace": "ui-skills",
  "update": "review",
  "include": ["improve-ui", "baseline-ui"]
}

Tous les champs, un par un

ChampDéfautÀ quoi ça sert
id—Obligatoire. Doit égaler le nom du fichier.
type—"github" ou "web-catalog".
repository—Format owner/nom. Rejeté sinon, avant tout appel réseau.
refbranche par défautBranche ou tag. Épingler un tag = figer la version.
rootstout le dépôtSous-dossiers où chercher des SKILL.md. Réduit le bruit et évite les faux positifs.
namespacenom du dépôtPréfixe des ids générés. Évite qu'un design-system de deux dépôts se percute.
includetoutListe blanche de slugs. Le slug = nom du dossier contenant le SKILL.md.
excluderienListe noire. Prioritaire sur include.
update"review"Voir §07.
maxFileBytes524288Plafond par fichier. Au-delà : ignoré et consigné dans skippedAssets.
maxFiles200Garde-fou. Un skill au-delà fait échouer la source plutôt que d'aspirer un monorepo.
downloadBinariesfalseVoir §09.
notes—Libre. Pour ton futur toi : pourquoi cette source existe.

Namespace, slug et id public

Sur disque : catalog/capabilities/<namespace>/<slug>/. L'id public est dérivé de namespace + slug, avec déduplication si le slug répète déjà le namespace — voir capabilityIdFor() dans src/core/names.ts. Les capabilities locales utilisent le namespace réservé local ; leur id public est simplement le slug.

local/landing-page/               →  landing-page
ui-skills/improve-ui/             →  ui-skills-improve-ui
matt-pocock/codebase-design/      →  matt-pocock-codebase-design
ui-skills/ui-skills-root/…        →  ui-skills-root  (pas de doublon)
Collisions et ownership

Une source externe ne peut jamais écraser une capacité locale (dossier sans SOURCE.json) ni prendre le contrôle d'une capacité appartenant à une autre source. La synchronisation vérifie le sourceId et l'id de capability avant toute écriture, et refuse explicitement en cas de conflit.

04Ajouter un catalogue web

Un catalogue (agent-design.com, une page « awesome-skills », un annuaire) ne contient pas les skills — il contient des liens vers eux. MCPIMP le traite donc comme une source de découverte, pas de contenu.

  page du catalogue
        │
        │  on extrait les liens github.com/owner/repo
        ▼
  owner/repo  ──────► le contenu est importé DEPUIS GITHUB
        │
        └──► le catalogue est conservé comme `discoverySource`

On ne scrape jamais le HTML du catalogue dans le registry. On s'en sert pour trouver la source d'origine, puis on importe proprement depuis elle, avec son commit et sa licence.

catalog/sources/agent-design.json
{
  "id": "agent-design",
  "type": "web-catalog",
  "url": "https://agent-design.com/skills",
  "roots": [".claude/skills"],       ← appliqué à CHAQUE dépôt délégué
  "namespace": "ui-ux-pro-max",
  "include": ["ui-ux-pro-max"],      ← idem
  "allowedRepositories": ["nextlevelbuilder/ui-ux-pro-max-skill"]
}
Pourquoi allowedRepositories est obligatoire

Sans ça, n'importe qui capable de faire ajouter son dépôt au catalogue pourrait injecter une capacité dans ton MCPIMP. La page est un contenu tiers que tu ne contrôles pas. Liste vide = découverte seule : la sync te dit ce qu'elle a trouvé, et n'importe rien.

La liste des « non autorisés » qui revient à chaque run

C'est le mode découverte qui fait son travail : il te montre le catalogue d'options. Pour en adopter un, tu l'ajoutes à allowedRepositories et tu relances.

Piège d'affichage connu

ibelick/ui-skills apparaît dans cette liste alors qu'il est bien importé. Ce n'est pas une contradiction : il l'est via sa propre source (catalog/sources/ibelick-ui-skills.json), pas via le catalogue — et le catalogue, lui, n'a pas le droit de l'importer. La liste devrait exclure les dépôts déjà couverts ailleurs ; ce n'est pas encore le cas.

05Recettes par cas d'usage

Les situations que tu vas réellement rencontrer.

AUn dépôt = un seul skill, à la racine

Le SKILL.md est à la racine. Pas de roots, pas d'include.

{
  "id": "emilkowalski-skill",
  "type": "github",
  "repository": "emilkowalski/skill",
  "namespace": "emil"
}
Le slug devient le nom du dépôt → id emil-skill.
BUn dépôt multi-skills

Chaque sous-dossier avec un SKILL.md devient une capacité. Rien à coder par skill.

{
  "id": "addyosmani-agent-skills",
  "type": "github",
  "repository": "addyosmani/agent-skills",
  "roots": ["skills"],
  "namespace": "addy"
}
Lance d'abord sans --apply : tu verras la liste complète de ce qui serait importé, et tu pourras affiner avec include.
CLes skills sont dans un dossier caché

Fréquent avec les plugins Claude Code : .claude/skills/. Ça marche, il faut juste le déclarer explicitement.

{
  "roots": [".claude/skills"]
}
Ces skills sont souvent platform-specific (ils attendent ${CLAUDE_PLUGIN_ROOT}). C'est détecté et consigné, mais à toi de juger si c'est utilisable hors de Claude Code.
DJe ne veux que 2 skills sur 12 
{
  "include": ["improve-ui", "fixing-accessibility"]
}
Les slugs sont les noms de dossiers, pas les name: du frontmatter. En cas de doute, fais un run à blanc : les ids affichés te donnent les slugs.
EFiger une version précise

Un tag au lieu d'une branche : la source ne bougera plus jamais toute seule.

{
  "ref": "v2.1.0",
  "update": "manual"
}
FLe skill embarque des images ou des polices

Par défaut, les binaires ne sont pas téléchargés : ils sont recensés dans skippedAssets avec leur taille, leur SHA et leur URL. Tu gardes la trace sans alourdir le dépôt.

Si tu en as vraiment besoin localement :

{
  "downloadBinaries": true,
  "maxFileBytes": 2097152
}
Pense au poids : le skill ui-styling d'ui-ux-pro-max embarque 80+ polices .ttf.
GLe skill contient des scripts

Ils sont importés comme du texte inerte, indexés, cherchables — et jamais exécutés par MCPIMP, à aucun moment. La capacité est classée executable pour que l'IA le sache.

Si tu veux réellement en exécuter un un jour, ça devra passer par un tool MCP dédié et explicite. Ce n'est pas dans le périmètre actuel.

HRetirer une source

Deux gestes, aucun automatisme :

rm catalog/sources/ma-source.json
rm -rf catalog/capabilities/local/ma-capacite
La sync ne supprime jamais rien d'elle-même. Si un skill disparaît en amont, sa capacité locale cesse simplement d'apparaître dans le rapport — elle reste sur disque.

06Le cycle de synchronisation

Ce qui se passe à chaque run

1. lire catalog/sources/*.json                    (disque)
2. pour chaque source GitHub :
     GET /repos/{owner}/{repo}                → branche par défaut, licence
     GET /repos/{owner}/{repo}/commits/{ref}  → LE commit
     GET /git/trees/{commit}?recursive=1      → tout l'arbre, avec un SHA
                                                 par fichier
3. regrouper les fichiers par dossier contenant un SKILL.md
4. contentHash = sha256( chemin+SHA de chaque fichier, trié )
5. comparer au contentHash du SOURCE.json local
        │
        ├── identique  → ✓ up-to-date        AUCUN téléchargement
        └── différent  → ↑ update-available  + liste des fichiers changés
6. si (et seulement si) l'écriture est autorisée :
     télécharger les fichiers, écrire upstream/, réécrire SOURCE.json
Le truc malin : 3 requêtes par dépôt

L'arbre Git renvoie le SHA de chaque fichier sans télécharger leur contenu. On peut donc savoir précisément ce qui a changé — et même quels fichiers — sans transférer un seul octet de contenu. Un dépôt inchangé coûte 3 requêtes, point.

Les statuts

SymboleStatutSignification
✓up-to-dateRien n'a bougé. Aucun réseau de contenu, aucune écriture.
↑update-availableNouvelle révision. Les fichiers ajoutés / modifiés / supprimés sont listés.
−removed-upstreamLa capability n'est plus découverte en amont. La copie locale est conservée pour une décision explicite.
→renamed-upstreamLe même chemin amont produit maintenant un autre id de capability. Les deux ids sont signalés.
+newJamais importée. S'applique dès --apply.
✗unavailableInjoignable, invalide, ou refusée par un garde-fou. N'interrompt pas les autres sources.

Les commandes

pnpm sources:sync

Lecture seule. N'écrit jamais rien. À lancer sans crainte.

pnpm sources:sync --apply

Écrit les nouveaux imports et les updates en politique auto.

pnpm sources:sync --apply <capacité>

Accepte une mise à jour retenue par review.

pnpm sources:sync --apply <source>

Idem pour toutes les capacités de cette source. Cibler la source limite aussi le parcours réseau ; cibler une capacité ne le peut pas.

pnpm sources:sync --json

Sortie machine, pour scripter ou brancher sur une CI.

pnpm capabilities:review

Liste les capabilities importées dont le contenu exact demande encore une revue.

pnpm capabilities:review -- <capability> --reviewer <nom>

Atteste le contentHash actuellement installé. Cette action reste locale et explicite.

Pourquoi cibler une capacité ne réduit pas le scan

Une capacité n'existe qu'après la découverte : impossible de savoir quelle source la produit avant d'avoir lu les dépôts. La cible n'agit donc qu'au moment de décider d'écrire. Un id de source, lui, est connu d'avance et restreint le run (src/ingestion/sync.ts, ~ligne 227).

07Politique d'update

Le problème qu'on résout : un dépôt tiers peut modifier son SKILL.md du jour au lendemain. Si MCPIMP avalait ça automatiquement, le comportement de ton IA changerait sans que tu l'aies décidé. D'où trois niveaux.

PolitiquePremier importMise à jourPour quoi
auto--apply--applyUne source que tu contrôles (ton propre dépôt).
review (défaut)--apply--apply + nommer la cibleTout le reste. Tu vois le diff avant d'accepter.
manual--applyidem reviewMarqueur d'intention : « ne touche pas sans réfléchir ».

Le premier import s'applique dès --apply, quelle que soit la politique : déclarer une source est déjà un acte volontaire. La politique protège l'évolution, pas l'adoption. La logique tient en cinq lignes — mayWrite() dans src/ingestion/sync.ts.

À quoi ressemble une update retenue
↑ ui-skills-improve-ui               update-available
    revision fdc667270f → 9a3f21c8e0
    +1 ~1 -0
      + references/checklist.md
      ~ SKILL.md
    policy "review": run sources:sync --apply ui-skills-improve-ui to accept

08Modifier un skill sans casser la resync

Le réflexe naturel — éditer upstream/SKILL.md — est le piège : la prochaine sync remplace tout upstream/ et ta modification disparaît. Utilise overrides/.

Ajouter un fichier
overrides/
  mcpimp-notes.md

Nouveau chemin → s'ajoute à la capacité.

Remplacer un fichier
overrides/
  references/plan.md

Même chemin qu'en amont → ta version gagne.

Le champ layer de chaque fichier (visible via capability-info) te dit d'où il vient : upstream ou override. Utile pour auditer ce que tu as dévié.

Limite assumée

Un override remplace le fichier amont, il ne fusionne pas. Si l'amont améliore un fichier que tu as override, tu ne récupères pas ses changements automatiquement — la sync te signalera qu'il a bougé, à toi de reporter. C'est le prix de la simplicité ; une fusion à trois voies serait disproportionnée ici.

09Binaires et types de skills

Pourquoi c'était un vrai problème

Le registry lisait tous les fichiers en UTF-8. Une image ou une police dans un skill externe, et l'index se remplissait de charabia — voire plantait. Maintenant, trois tests en cascade : extension connue comme binaire, présence d'un octet NUL, validation UTF-8 stricte. Au moindre doute, le fichier n'est pas décodé.

Fichier texte — indexé, cherchable, lisible via resources/read.
Fichier binaire — métadonnées conservées (taille, type MIME, sha256), exclu des ressources lisibles ; resources/read renvoie une erreur explicite plutôt qu'un contenu corrompu.

Les 4 types de skills détectés

Déterminé à l'import, consigné dans SOURCE.json, purement informatif — ça ne bloque jamais un chargement.

TypeDéclencheurCe que ça implique
portableSKILL.md + references/Utilisable partout, sans condition.
resource-dependentdata/, assets/, binairesA besoin de ses fichiers pour être utile.
executablescripts/, .py, .sh…Contient du code. MCPIMP ne l'exécute jamais.
platform-specific${CLAUDE_PLUGIN_ROOT}, .claude-pluginDépend d'un hôte précis. Peut ne rien donner ailleurs.

La priorité est décroissante : un skill avec des scripts et un marqueur de plateforme est classé platform-specific. Les indices bruts sont conservés à part dans skillTraits. Logique dans classifySkill(), src/ingestion/normalize.ts.

10Régler la recherche

Avec 3 capacités, un includes() suffisait. Avec 9 — et à terme des centaines — il fallait un classement. src/registry/search.ts calcule un score en six temps.

1. poids par champ

Le nom et la description de la capacité pèsent 6 et 4 ; le corps du texte pèse 1. Un mot dans un titre compte plus qu'au milieu d'un paragraphe.

2. IDF

Un mot présent dans tous les fichiers n'apporte aucune information et ne fait donc rien remonter.

3. couverture

Un fichier qui matche 3 mots sur 3 écrase celui qui n'en matche qu'un. C'est ce qui rend les requêtes multi-mots utiles.

4. poids par type

Un SKILL.md ×1.4, un BUNDLE.md ×0.35 (il concatène tout, donc il matche n'importe quoi), un script ×0.5.

5. intention ressource

Quand la requête cherche une ressource, une référence, un lien, un catalogue ou de l'inspiration, les capacités de ressources et les fichiers references/ reçoivent un boost ciblé.

6. bonus de phrase

×1.6 si la requête apparaît telle quelle.

Le pont français / anglais

Tes capacités sont écrites en français, les IA interrogent souvent en anglais. src/registry/synonyms.ts contient des groupes de mots équivalents, comptés à poids réduit (0.4). C'est ce qui fait que photographic luxury retrouve un texte parlant d'imagerie et de haut de gamme.

// ajouter ton propre vocabulaire métier :
["hospitality", "hotel", "hotellerie", "restaurant", "resort"],
["luxury", "luxe", "premium", "upscale", "elegant"],
["saas", "abonnement", "subscription", "b2b"],   ← à toi

Contrainte : un seul token par entrée, en minuscules sans accent. « haut-de-gamme » ne marcherait pas — le tokenizer le découperait.

Le jour où tu voudras du vrai sémantique

Ce n'est pas de la recherche sémantique, et ça ne prétend pas l'être. Le point de remplacement est unique : la fonction expandTerm(). Y brancher des embeddings ne touche aucun autre fichier. C'était le but de la découpe.

11Étendre le code

Le cas le plus probable : tu veux importer depuis autre chose que GitHub — un GitLab, un Git nu, une API interne, un sitemap.

Les deux ports

Dans src/ingestion/types.ts. La distinction est importante : certaines sources contiennent du contenu, d'autres se contentent d'indiquer où il est.

// Source de CONTENU : on peut fetcher dedans
interface ContentSourceAdapter<D> {
  type: string;
  getRevision(source: D): Promise<SourceRevision>;              // pas cher
  discover(source: D, rev: SourceRevision): Promise<DiscoveredSkill[]>;
  fetch(source: D, skill: DiscoveredSkill): Promise<FetchedFile[]>; // si changé
}

// Source de DÉCOUVERTE : elle délègue à une source de contenu
interface DiscoverySourceAdapter<D> {
  type: string;
  getRevision(source: D): Promise<SourceRevision>;
  discoverSources(source: D): Promise<DelegatedSource[]>;
}

Checklist pour un nouvel adapter de contenu

1. src/ingestion/types.ts — ajoute ton interface de définition et mets-la dans l'union SourceDefinition.
2. src/ingestion/definitions.ts — ajoute une branche dans parseSourceDefinition() pour valider tes champs. Valide vraiment : c'est la seule barrière avant le réseau.
3. src/ingestion/gitlab.ts — implémente ContentSourceAdapter. Passe par fetchJson/fetchBytes de http.ts pour hériter des plafonds et des timeouts, et ajoute ton hôte via extraHosts.
4. src/ingestion/sync.ts — le point dur, voir ci-dessous.
5. Un test avec un faux serveur. Copie src/ingestion/__tests__/fake-github.ts : il stubbe fetch et te laisse simuler un push.
Limite actuelle à connaître

sync.ts code en dur l'adapter GitHub. Ligne ~252 :

if (source.type !== "github") continue;

Avec un seul adapter de contenu, une table de dispatch aurait été de l'abstraction gratuite. Au deuxième, elle se justifie : remplace ce test par une Map<string, ContentSourceAdapter> et récupère l'adapter par source.type. Le reste de la boucle est déjà générique — elle ne manipule que des DiscoveredSkill.

Le contrat à respecter

Trois règles, sinon tu casses les garanties du système :

Ne télécharge rien dans discover().

C'est ce qui rend « inchangé = gratuit » vrai. Si ta source n'expose pas de hash par fichier, utilise ETag, Last-Modified, ou un hash de ce que tu peux obtenir sans coût.

Fais passer chaque chemin par assertSafeRelativePath().

Ces chaînes viennent d'un tiers et vont devenir des écritures disque.

Ne perds jamais la révision exacte.

Remplis origin avec ce que tu as de plus précis. Sans identifiant stable, un hash du contenu vaut mieux que rien.

12Sécurité

Un SKILL.md récupéré sur Internet est un fichier écrit par un inconnu, qui sera ensuite lu par une IA. C'est exactement le profil d'une injection de prompt. Les garde-fous :

Aucune exécution. Les scripts importés sont du texte. Rien n'est lancé, ni à l'import ni au chargement.
Aucune interprétation à l'ingestion. L'ingester lit des octets et des chemins. Il ne « suit » jamais ce qui est écrit dans un fichier.
Bannière de provenance. load-capability préfixe tout contenu importé d'un rappel : ce texte est une référence, pas une autorité. Une IA qui lit « ignore previous instructions » dedans a le contexte pour le refuser.
Réseau contraint. HTTPS obligatoire, liste blanche d'hôtes, plafonds de taille, timeouts.
Écritures confinées. Chemins validés contre la traversée, segments namespace/slug validés, et chaque écriture re-vérifiée comme étant sous catalog/capabilities/.
Aucun secret exposé. Un GITHUB_TOKEN n'est envoyé qu'à api.github.com, jamais à un hôte tiers.
Ce que ça ne protège pas

Un skill importé peut contenir de mauvais conseils de design, ou des instructions persuasives. Le système garantit qu'il ne s'exécute pas et qu'il est identifié comme externe — pas qu'il est bon. La politique review existe pour que tu lises avant d'accepter.

13Dépannage

"id" must match the filename

Le champ id et le nom du fichier diffèrent. Renomme l'un des deux.

GitHub tree … is truncated

Le dépôt est trop gros pour un arbre en une requête. Ajoute roots pour cibler le sous-dossier des skills. On refuse plutôt que d'importer un skill partiel.

HTTP 403 for https://api.github.com/…

Quota atteint : 60 requêtes/heure sans authentification. Mets un GITHUB_TOKEN dans .env.

Host not allowed for source ingestion

Hôte hors liste blanche. Pour un catalogue, son propre domaine est autorisé automatiquement ; pour autre chose, passe par extraHosts dans ton adapter.

Unsafe upstream path

Un chemin amont contient .., un chemin absolu ou un segment réservé. Le fichier est ignoré — c'est le garde-fou qui fonctionne.

Une capacité n'apparaît pas après l'import

Le registry requiert au moins un composant supporté (aujourd'hui SKILL.md ou mcp.json) dans upstream/ (ou overrides/). Vérifie aussi qu'aucune capacité locale ne porte le même id — la locale gagne.

Mes modifications ont disparu

Tu as édité upstream/. Refais-les dans overrides/, au même chemin relatif.

Le déploiement Cloudflare ne voit pas les nouveaux skills

Le Worker sert un snapshot figé. Relance pnpm run build après chaque sync pour régénérer generated/capability-snapshot.ts.

Code de référence : src/ingestion/ (ingestion), src/registry/ (index et recherche), catalog/sources/ (déclarations), catalog/capabilities/<namespace>/<slug>/ (résultat).

Validation : pnpm run test · pnpm run typecheck · pnpm run build.
